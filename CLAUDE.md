# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A Rust library crate (`actix-web-oidc-bff`): a Backend-for-Frontend OIDC relying party for actix-web. The authorization-code + PKCE flow happens server-side; tokens never reach the browser — the cookie carries only a session reference. There is no binary; consumers mount the routes into their own actix-web app.

## Commands

```sh
cargo build
cargo test                      # all tests (unit tests live in #[cfg(test)] modules per file)
cargo test some_test_name       # run a single test by name substring
cargo test config::             # run all tests in one module
cargo clippy --all-targets
cargo fmt
cargo deny check                # advisories + licenses + bans + sources (CI runs this)
cargo deny check advisories     # just the RustSec database
```

Supply chain: use `cargo deny check`, **not** `cargo audit`. The advisory policy — including the documented `RUSTSEC-2023-0071` (`rsa`) ignore and its re-evaluation triggers — lives in `deny.toml` at the repo root. `cargo audit` does not read that file (it used to read a since-deleted `.cargo/audit.toml`), so a bare `cargo audit` now exits non-zero on `rsa` with no visible justification. Install with `cargo install --locked cargo-deny`.

Note: the crate reads **no** environment variables. `config.rs` tests used to mutate process env and were serialized via a `static ENV_LOCK: Mutex`; both the env tests and the lock are gone, and config tests now run fully in parallel because the builder is pure. Do not reintroduce env-mutating tests — build a config with `OidcBffConfig::builder()` instead.

## Architecture

The crate wires together eight concerns; the flow spans multiple files:

1. **`session_state.rs` — constants + pre-auth machinery**: defines all session key constants (`SUB`, `ISS`, `EMAIL`, `NAME`, `ACCESS_TOKEN`, `REFRESH_TOKEN`, `ID_TOKEN`, `CLAIM_KEYS`, `PRE_AUTH`, `LOGIN_AT`) and the hand-maintained `RESERVED_SESSION_KEYS` array. `LOGIN_AT` (`__bff_login_at`) is the absolute-lifetime anchor: stamped by the callback immediately after `session.renew()`, read by the `Auth` extractor and `DbSessionStore`, deliberately **not** in `POST_AUTH_SCRUB_KEYS` (every successful login overwrites it) and never exposed through `Auth::claims`. It ships with `LOGIN_AT_FUTURE_SKEW_SECS = 60` (clock-skew allowance for a timestamp slightly in the future) and `login_at_from_json` (interprets an already-deserialized value as epoch seconds). **`RESERVED_SESSION_KEYS` is NOT derived mechanically** — when adding a new session key constant you must also add it to `RESERVED_SESSION_KEYS`; the `reserved_keys_cover_every_constant` test enforces membership. Also exports `POST_AUTH_SCRUB_KEYS` (all token/identity keys minus always-overwritten `SUB`/`ISS`), `PRE_AUTH_MAX_SLOTS = 5`, `PreAuthEntry`, and the pre-auth slot helpers (`push_pre_auth`, `take_matching`, `prune_expired`) plus `insert_or_internal` (logs the real error, maps to `BffError::Internal`). `take_matching` calls `constant_time_eq` unconditionally for every slot — no cross-slot early exit — so timing does not reveal which slot matched.

   **`PreAuthEntry::max_age_secs: Option<i64>`** (added 0.3.0) carries a login variant's `require_auth_within` requirement from the login route to the callback, and is the **one** thing a variant is allowed to put into a slot. The exception is deliberate and bounded: it is a single integer, and `/auth/callback` is shared by every login route, so without it the callback genuinely cannot know the flow asked for anything. Extra authorization *parameters* still must never be stored here — see the size-budget invariant below. It carries `#[serde(default, skip_serializing_if = "Option::is_none")]`. `skip_serializing_if` is the load-bearing half: without it every slot pays `"max_age_secs":null` (~20 bytes × up to 5 slots) even for consumers who register no step-up variant at all, against a budget that is already tight. `default` is belt-and-braces — serde already maps a missing `Option` field to `None`, so slots written by an older version deserialize either way — but it becomes load-bearing the moment the field stops being an `Option`, so keep it. It is **not** a session key and therefore not in `RESERVED_SESSION_KEYS` — it is a field inside the `PRE_AUTH` vec's entries.

   **Rollout caveat, inherent rather than fixable:** during a rolling deploy an *old* instance serving `/auth/callback` does not know the field exists and will complete a step-up login without verifying it. The exposure is bounded by how long both versions serve simultaneously and by `pre_auth_ttl`. If that matters for a given deployment, drain rather than rolling-deploy the release that introduces a step-up variant.

2. **`config.rs` — `OidcBffConfig` + `OidcBffConfigBuilder`**: **code-first configuration; the crate reads no environment variables.** `OidcBffConfig::builder()` is the only construction path (`from_env()` and all `OIDC_*` vars were removed in 0.2.0). **Every field is private**, with public getters (`redirect_url()`, `scopes()`, `post_auth_ttl() -> Duration`, …); the sole exception is `allowed_origin`, which is `pub(crate)` because middleware/handler code reads it directly. `client_secret` has **no public getter at all** (only a `pub(crate)` one for `oidc.rs`). `OidcBffConfig` is deliberately not `#[non_exhaustive]` — private fields already prevent external construction and destructuring; only `ConfigError` carries that attribute. Holds issuer/client credentials, cookie settings (`__Host-` prefixed cookie when the redirect URL is https), scopes, TTLs (stored/exposed as `std::time::Duration`), `return_to_prefix`, `persist_claims`, `callback_passthrough_params`, `session_expiry`, `max_session_lifetime`, and `post_logout_redirect_url`. Also precomputes `pub(crate) allowed_origin: String` — the ASCII origin of `redirect_url` (scheme+host+port, default ports omitted) — for CSRF checks.

   **All setters are infallible; every check lives in `build()`**, which rejects: missing required fields, including ones set to an empty or whitespace-only string (reported together via `MissingFields`); `persist_claims` entries that collide with `RESERVED_SESSION_KEYS` (imported from `session_state.rs`); OIDC validation-artifact claim names (`aud`, `exp`, `iat`, `nbf`, `nonce`, `at_hash`, `c_hash`) — these have no persistence use and invite confusion; a `return_to_prefix` that fails `validate_return_to`; a session key that is not 64 bytes; a `post_auth_ttl` greater than `max_session_lifetime`; TTL `Duration`s that are not a whole number of seconds, are under one second, or exceed `MAX_TTL_SECS` (365 days) — `duration_to_ttl_secs` rejects sub-second values rather than truncating them to `0`, which would silently break login and escape `DbSessionStore::from_config`'s positivity assumption; `post_logout_redirect_url` values that are not valid http/https URLs, have an opaque/hostless origin, or are plain http when the redirect URL is https; and `callback_passthrough_params` entries that are malformed, duplicated, deny-listed, or exceed `MAX_PASSTHROUGH_PARAMS`.

   **`callback_passthrough_params(..)` / `callback_passthrough_params() -> &[String]`** (added 0.3.0, default empty = pre-0.3 behaviour): the allowlist of query-parameter names the callback forwards from the IdP's callback request onto the post-login redirect URL. Like `persist_claims`, repeat calls **replace** rather than append — a second call must not be able to smuggle a denied name past the first call's deferred validation. `normalize_passthrough_params` (in `config.rs`) trims, drops empties, then enforces: at most `MAX_PASSTHROUGH_PARAMS = 8` **surviving** names (the cap counts what is left after trimming), `validate_param_name(name, DENIED_PASSTHROUGH_PARAMS)` from `param_names.rs`, and no duplicates. Every failure is `ConfigError::InvalidPassthroughParam(String)`.

   Session key: no default. One of `session_key(key: actix_web::cookie::Key)` (a constructed `Key`, not raw bytes), `session_key_base64(s: impl AsRef<str>)` (ASCII whitespace stripped before decoding, so line-wrapped `openssl rand -base64 64` output is accepted), or the explicit `generate_ephemeral_session_key()` is required — the old silent random-key-with-a-warning fallback is gone. `jwks_ttl` is deliberately **not** settable (fixed 900 s): a long JWKS cache keeps revoked IdP signing keys trusted.

   `impl FromStr for SessionExpiry` (`"fixed"` / `"sliding"`, case-insensitive) exists solely so a consumer reading their own env var can parse it; nothing in the crate calls it.

   `ConfigError` typed variants: `MissingFields(Vec<&'static str>)`, `InvalidSessionKey`, `InvalidRedirectUrl`, `InvalidPostLogoutRedirectUrl`, `InvalidReturnToPrefix`, `ReservedClaimName`, `InvalidTtl`, `InvalidPassthroughParam`. `ConfigError` is `#[non_exhaustive]`.

3. **`oidc.rs` — `OidcRp`**: OIDC discovery + cached client. Key design points:
   - `BffExtraProviderMetadata` (not `EndSessionMetadata`) captures `end_session_endpoint` and `revocation_endpoint` from the discovery document.
   - `struct RpInner { metadata: BffProviderMetadata, client: Arc<BffClient> }` is held behind `Arc<RwLock<RpInner>>`. The client is rebuilt once per (re)discovery — `client()` returns `Arc<BffClient>` (a clone of the cached Arc, not a deep clone of the client).
   - **Hard constraint**: the network fetch in `refresh_metadata()` is performed before taking the write lock on `RpInner` — the write lock is never held across an `await`. Violating this deadlocks.
   - HTTP timeouts: `HTTP_TIMEOUT = 10s`, `HTTP_CONNECT_TIMEOUT = 5s` on the shared client. These are compile-time constants (deliberate — an env knob is an easy follow-up if needed). The client has redirect `Policy::none()` to prevent SSRF via malicious provider responses.
   - `allowed_algs() -> &'static [CoreJwsSigningAlgorithm]` is backed by a 9-element static array of RS\*/PS\*/ES\* algorithms. `HS*` and `none` are excluded at compile time.
   - `force_refresh_for_retry() -> bool`: called by the callback after an ID-token validation failure. Stampede-guarded via `try_write` on `last_forced_refresh: RwLock<Option<Instant>>`, rate-limited to one attempt per `FORCED_REFRESH_MIN_INTERVAL = 60s`. Returns `true` only on a successful refresh. Worst-case callback retry latency with three sequential 10s HTTP timeouts is ~30 s — operators should set upstream timeouts (e.g. load-balancer request timeout) accordingly.
   - `end_session_endpoint()` / `revocation_endpoint()` read from `inner.metadata.additional_metadata()`.
   - `#[cfg(test)]` helpers: `test_metadata(extra: BffExtraProviderMetadata) -> BffProviderMetadata` (builds a minimal discovery doc via `serde_json::from_value`); `for_tests(metadata) -> OidcRp` (client_id "test-client", secret "test-secret", redirect "https://app.example.com/auth/callback", jwks_ttl 1h, `last_refresh = now`).

4. **`handlers/` + `routes.rs`**: four routes registered by `configure()`, plus any number of consumer-registered **login-variant** routes:
   - `GET /auth/login` — validates `return_to` (open-redirect defense) and applies a **boundary-aware prefix check**: `return_to` must equal `cfg.return_to_prefix` or start with it and be followed by `/`; prefix `/app` accepts `/app` and `/app/sub` but rejects `/appointments` and `/app-evil`. An empty `return_to` query parameter is treated as absent and defaults to `cfg.return_to_prefix`. Generates state/nonce/PKCE, loads the `PRE_AUTH` vec from the session, prunes expired entries, pushes the new `PreAuthEntry` (FIFO-evicts at `PRE_AUTH_MAX_SLOTS = 5`), and writes the vec back in a single `insert_or_internal` call. The vec is keyed `oidc_pre_auth` and supports up to 5 concurrent login attempts (e.g. multiple tabs). `openid` is filtered from `cfg.scopes` before `authorize_url` to avoid duplicating it (the library adds it automatically). PKCE S256 is unconditional.
   - **Login variants** (added 0.3.0, same file): `ExtraAuthParams::new(params) -> Result<Self, AuthParamError>` (`Clone + PartialEq + Eq`, plus `is_empty`/`len`) validates a fixed set of extra authorization-request parameters at construction — `MAX_EXTRA_AUTH_PARAMS = 8`, `MAX_EXTRA_AUTH_VALUE_LEN = 512`, `has_control_chars` on values, no duplicate names (ASCII-case-insensitive, matching the deny-list check), and `validate_param_name(name, DENIED_AUTH_PARAMS)` from `param_names.rs`. Its `Debug` is **hand-written to redact every value** and print names only: `AuthParamError` is careful never to carry a value, and a derived `Debug` would undo that the first time a set reached a log line or panic message (`login_hint` carries personal data). Do not replace it with a derive. `login_route(params: ExtraAuthParams) -> actix_web::Route` builds a route running the same login handler with those parameters applied via openidconnect's typed `add_extra_param` (correct URL-encoding, no manual string building). `login_route`, `ExtraAuthParams`, and `AuthParamError` are re-exported at the crate root; the `MAX_EXTRA_AUTH_PARAMS` / `MAX_EXTRA_AUTH_VALUE_LEN` / `MAX_AUTH_AGE_SECS` / `AUTH_TIME_SKEW_SECS` constants stay `pub` in `handlers::login`.

     **`require_auth_within(self, max_age: Duration) -> Result<Self, AuthParamError>`** (with the `auth_max_age() -> Option<Duration>` getter) is verified re-authentication, and is the **only** way `max_age` can reach the authorization URL. Three effects as one unit: (a) `login_impl` calls openidconnect's typed `set_max_age` — never `add_extra_param` — so exactly one `max_age` is emitted and it is correctly encoded; (b) the requirement is stored as `PreAuthEntry::max_age_secs`; (c) the callback's step (8) verifies the resulting `auth_time` claim. `max_age` is on `DENIED_AUTH_PARAMS`, so a raw `("max_age", "300")` pair is an `AuthParamError::ReservedName` — the point being that the hand-rolled form transmits the request and verifies nothing, which is worse than not offering it. Rejects sub-second `Duration`s (rather than truncating, matching `duration_to_ttl_secs` in `config.rs`) and anything over `MAX_AUTH_AGE_SECS = 365 * 24 * 3600`, both as `AuthParamError::InvalidMaxAge`. `AUTH_TIME_SKEW_SECS = 60` is the clock-skew allowance applied in both directions by the callback check (mirroring `LOGIN_AT_FUTURE_SKEW_SECS`); `Duration::ZERO` is legal and the skew is what keeps a genuine round trip from failing it. Note `is_empty()`/`len()` report on the name/value pairs only — a set carrying only a freshness requirement is still "empty" by that measure. **`GET /auth/login` is byte-for-byte unchanged when no variant is registered** — the empty `ExtraAuthParams` path must add nothing to the authorization URL. `configure()` does **not** register variants; consumers mount them themselves at a path of their choosing. The `deny_list_covers_every_crate_set_authorize_param` test lives here: it builds a real authorization URL and asserts every parameter name the crate emits appears in `DENIED_AUTH_PARAMS`.
   - `GET /auth/callback` — takes `HttpRequest` as its **first argument** (added 0.3.0, source-breaking for direct callers; `configure()` users are unaffected) so it can read the raw callback query string (`req.query_string()`) for passthrough. Fifteen numbered steps: (1) removes the `PRE_AUTH` vec from the session and prunes expired entries; (2) handles IdP `error` params: if `state` is present, consumes only the matching slot and writes the remainder back; if `state` is absent, writes the full (pruned) vec back untouched — a stateless error redirect must not nuke concurrent tabs' slots; (3) requires code+state, writing the vec back first; (4) `take_matching` with constant-time comparison across all slots; writes `rest` back before any later failure path; (5) reconstructs the PKCE verifier from the matched slot; (6) exchanges the code; (7) validates the ID token against the static allowed algs; on failure: `force_refresh_for_retry()`, retry once, else 400; (8) if the matched slot carries `max_age_secs`, `verify_auth_freshness(claims.auth_time(), max_age_secs, now)` — **must** stay ahead of `session.renew()` and every session write below, or a rejected step-up would still leave a usable authenticated session behind; **fails closed on an absent `auth_time`** (OIDC Core makes the claim REQUIRED when the request carried `max_age`, so its absence *is* the silent-downgrade signal), rejects an age over `max_age_secs + AUTH_TIME_SKEW_SECS` and an `auth_time` more than `AUTH_TIME_SKEW_SECS` in the future, all three as `BffError::BadRequest("Re-authentication required")` with a `log::warn!` that names the age and never the token; (9) `session.renew()` against session fixation; (10) stamps `LOGIN_AT` — **must** be immediately after `renew()` and before every fallible insert below, because `sub` present without `login_at` is treated as a dead session; (11) scrubs `POST_AUTH_SCRUB_KEYS` plus the old `CLAIM_KEYS` list; (12) inserts standard claims (`SUB`, `ISS`, optional `EMAIL`/`NAME`); (13) `serde_json::to_value(claims)` on the full `IdTokenClaims` struct and uses `select_claims` to pick `persist_claims` entries uniformly — no amr/acr special-case, the serialization flatten handles them; stores each value as `serde_json::Value` directly, then writes the `CLAIM_KEYS` list; (14) inserts tokens via `insert_or_internal`; (15) `append_passthrough(&return_to, req.query_string(), cfg.callback_passthrough_params())` builds the `Location` value, appending the allowlisted parameters that are actually present on the callback request, percent-encoded (returns a `Cow` so the empty-allowlist path allocates nothing). Constants `MAX_PASSTHROUGH_VALUE_LEN` (256, on the *decoded* value) and `MAX_PASSTHROUGH_TOTAL_LEN` (1024, on the *encoded* appended block) live in `callback.rs`: values over the per-value cap, containing control characters, or containing `U+FFFD` (percent-decoding is lossy — `%FF` arrives as the replacement character, so a bare control-character scan would miss it) are dropped with a `log::warn!` **naming the parameter and never the value**; a name already present in the `return_to` query is skipped; a pair that would breach the aggregate cap is skipped and the next one still tried (**not** `break` — the cap is spent in encoded bytes, which percent-encoding can inflate threefold, so one fat value must not starve the short parameters behind it). Only the **first** occurrence of a repeated name is considered and the drop decision is final — `selected[idx]` is an `Option<Option<String>>` precisely so "seen but dropped" is distinguishable from "not seen", which is what stops a clean second copy reviving a poisoned first one. Step (15) is **success-path only** — the step-(2) error path returns 400 and never redirects (`error_path_never_appends_passthrough_params` pins this). Finally, `is_safe_composed_redirect` re-checks the composed `Location` (starts with `/`; no `//`, `\`, or `:/` **anywhere**, matching `validate_return_to`; printable ASCII; within `MAX_COMPOSED_REDIRECT_LEN`) and, on failure, degrades to `cfg.return_to_prefix()` — **not** to `return_to`, which is the only value that could have failed the check. The guard is unreachable by construction; it is the same redundant-but-cheap style as `store.rs`'s expiry re-check on `load()`.
   - `POST /auth/logout` — (1) `ensure_same_origin_against(&req, &cfg.allowed_origin)` (fast path using precomputed origin); (2) reads `ID_TOKEN`, `REFRESH_TOKEN`, `ACCESS_TOKEN` **before** `session.purge()`; (3) resolves `end_session_endpoint` URL **before** purge — malformed URL: `log::warn!` including the endpoint value, degrade to 204 (revocation still runs); (4) `revoke_best_effort`: refresh preferred over access, uses a **parsed-scheme https guard** (`Url::parse(endpoint).map(|u| u.scheme() == "https")`) to reject non-https revocation endpoints when `cfg.cookie_secure` — the `url` crate lowercases schemes on parse so `HTTPS://...` is also accepted; this guard is inactive when `cookie_secure == false` (http dev deployments); malformed endpoint → not-https → skip + warn (fail-closed on transmission, fail-open on revocation); clones the cached `Arc<BffClient>` via `(*client).clone().set_revocation_url(url)`, calls `revoke_token(..).request_async(oidc.http_client())` using the **shared redirect-disabled, timeout-configured client** (never a freshly built client — that could follow redirects or lack timeouts), warn-and-continue on every failure, **never logs token values** (endpoint + error kind only); (5) `session.purge()`; (6) 200 + `{"idp_logout_url"}` or 204.
   - `GET /auth/me` — takes `Auth` extractor (401 produced by extractor when no `sub`); returns exactly `{"sub", "iss", "email", "name"}` — no tokens, no extra claims.
   Shared state (`OidcRp`, `OidcBffConfig`) is registered separately via `configure_app_data()`.

5. **`extractor.rs` — `Auth`**: `FromRequest` extractor for downstream handlers. Sync extraction via `future::ready(Auth::extract(req))`. Reads `sub` (401 if absent) plus standard fields from session-key constants. Rehydrates extra claims: reads the `CLAIM_KEYS` vec, then reads each claim as `serde_json::Value` directly (no double-decoding — callback now stores values as `Value`, not JSON-encoded strings).

6. **`store.rs` — `SessionRepository` / `DbSessionStore`**: bring-your-own persistent session storage (the crate has no DB dependency). `DbSessionStore` adapts a consumer-supplied `SessionRepository` to `actix_session::storage::SessionStore`, making sessions revocable server-side. The `load()` path enforces expiry regardless of whether the repository filtered the row (`s.expires_at <= Utc::now()` → best-effort `repo.delete()` + `Ok(None)`). This is defense-in-depth: compliant repos should filter on the DB side, but this catches stale rows from non-compliant ones or race conditions.

   **Pre-auth TTL cap**: `DbSessionStore` holds a `pre_auth_ttl_secs` field (default 600 s, matches the builder's `pre_auth_ttl` default) and applies `ttl_secs.min(pre_auth_ttl_secs)` in `save()` and `update()` for rows that do not contain the `SUB` session key (i.e., anonymous/pre-auth state). Authenticated rows use the full TTL. Override via `DbSessionStore::with_pre_auth_ttl_secs(secs)`, or — preferred — use `DbSessionStore::from_config(repo, &cfg)`, which wires both the pre-auth TTL and the max lifetime from the config. `DbSessionStore::new(repo)` silently keeps crate defaults regardless of the config; that is the footgun `from_config` exists to close. This caps the session-store DoS window for an unauthenticated flood of `/auth/login` requests; rate-limiting at the deployment level is still recommended.

   **`SessionRepository::update` contract**: `update` returns `Ok(true)` when the row was updated, `Ok(false)` when no such key exists (do not error for a missing key). The adapter interprets `false` (row vanished — purged or expired between load and write) with a **do-not-resurrect guard**: if the state contains any token key (`ACCESS_TOKEN`, `REFRESH_TOKEN`, `ID_TOKEN`), the write is dropped and the stale key is returned — purge is authoritative, a request racing logout cannot recreate a token-bearing row. For token-free state (pre-auth/anonymous) the adapter mirrors actix-session's Redis semantics: generates a new session key, inserts with the pre-auth-capped TTL (reusing the A-1 helper), and returns the new key to preserve multi-tab login ergonomics.

   **This is the only module allowed to use `anyhow`** — the `SessionStore` trait forces `anyhow::Error` into its signatures; everything else uses `BffError`/`ConfigError`/`DiscoveryError`/`RepoError`.

7. **`middleware.rs` — `session_middleware()`**: builds the hardened `SessionMiddleware` from the config (cookie name/Secure from config, HttpOnly, SameSite=Lax, Path=/, persistent TTL from `cfg.post_auth_ttl()`, expiry policy from `cfg.session_expiry()`). This is what makes the config's cookie/TTL fields actually take effect — consumers should wrap their `App` with it. Note: the middleware TTL applies to authenticated sessions; `DbSessionStore` independently caps the TTL for anonymous/pre-auth rows — these are two orthogonal settings.

8. **`param_names.rs` — shared parameter-*name* validation + two hand-maintained deny-lists** (module is `pub(crate)`; only `MAX_PARAM_NAME_LEN` is re-exported at the crate root, because both surfaces name it in their error messages). One `validate_param_name(name, denied) -> Result<(), ParamNameError>` serves both consumer-supplied parameter surfaces: non-empty, ≤ `MAX_PARAM_NAME_LEN` (64) bytes, charset `[A-Za-z0-9_.-]` (deliberately narrower than RFC 6749 — it excludes everything that could need percent-encoding, so a name can never smuggle `&`, `=`, or a control character into a query string), then an ASCII-case-insensitive deny-list check. `ParamNameError` is crate-internal on purpose; each surface maps it into its own public error type (`AuthParamError` / `ConfigError::InvalidPassthroughParam`) so neither leaks the other's vocabulary. `has_control_chars(value)` lives here too — it is the shared *value* rule for both surfaces (C0, DEL, C1), previously duplicated with two different spellings in `login.rs` and `callback.rs`. It is a URL-safety rule, not an "is safe to render" rule: `<`, `&` and quotes all pass, because percent-encoding neutralises them for the `Location` header.

   **Both `DENIED_AUTH_PARAMS` and `DENIED_PASSTHROUGH_PARAMS` are hand-maintained, exactly like `RESERVED_SESSION_KEYS` — they are NOT derived mechanically.** Adding a parameter that the crate itself puts on the authorization URL means adding it to `DENIED_AUTH_PARAMS` by hand; adding a callback parameter that must never reach a browser-visible URL means adding it to `DENIED_PASSTHROUGH_PARAMS` by hand. The lists are **independent**: `code` is fine as an authorize parameter and forbidden as a passthrough one; `prompt` is fine on both. Do not merge them "for simplicity".

   **`max_age` is on `DENIED_AUTH_PARAMS` for a reason unlike every other entry there.** The rest are denied because sending them would break or subvert the flow (a duplicated `state`, a JAR blob replacing the request, a credential in a front-channel URL). `max_age` is denied because it is **unverifiable in the hand-rolled form**: as a bare `add_extra_param` pair it transmits the request and checks nothing, so a provider that ignored it is indistinguishable from one that honoured it and the caller believes they have a guarantee they do not. `ExtraAuthParams::require_auth_within` sends it via the typed `set_max_age` *and* verifies the resulting `auth_time` claim in the callback, so denying the raw name is what makes the verified path the only path. Do not "fix" this by removing the entry because `max_age` looks harmless — harmlessness was never the criterion for this one. The mechanical `deny_list_covers_every_crate_set_authorize_param` test does cover it — it builds a variant URL with `require_auth_within` and asserts `max_age` is actually on that URL before checking the deny-list, so the coverage cannot silently lapse into vacuity. `policy_only_denied_auth_params_are_still_present` additionally pins the reason in its assertion message. Two tests guard the shape (`deny_lists_are_sorted_and_deduplicated`, `lists_are_independent`), and `DENIED_AUTH_PARAMS` additionally has a **mechanical completeness test in `handlers/login.rs`** (`deny_list_covers_every_crate_set_authorize_param`) that builds a real authorization URL and asserts every parameter name the crate emits is on the list.

   **That mechanical test is only half a safety net, and knowing which half matters.** It asserts *emitted ⊆ deny-list*, so it catches a parameter the crate **starts** emitting without a matching entry. It is structurally blind to the **deletion** of an entry the crate never emits — and those (`request`, `request_uri`, `response_mode`, `client_secret`, `client_assertion`, `client_assertion_type`, `code_verifier`) are exactly the entries that look like dead weight to someone tidying up. `request_uri` is the sharp one: a JAR request object replaces the entire authorization request and thereby bypasses every other entry including `redirect_uri`. `policy_only_denied_auth_params_are_still_present` in `param_names.rs` pins those seven by hand, with the reason in each assertion message; `credential_bearing_passthrough_params_are_still_denied` does the same for the passthrough list, which has no mechanical check at all because there is no enumerable source of truth for "must never appear in a URL".

### Error conventions

### Security invariants to preserve

- **Config fields stay private — private, not `pub(crate)`.** Before 0.2.0 they were `pub`, so every validation `from_env()` performed could be undone the line after it returned — `cfg.persist_claims.push("access_token".into())` makes the `Auth` extractor leak raw tokens, `cfg.cookie_secure = false` disables the https guard on logout revocation. Closing the fields is what turns these documented invariants into type-system invariants. `allowed_origin` is the one deliberate `pub(crate)` field; widening any other field to `pub(crate)` "for parity" is a regression, not a cleanup — in-crate code mutating `persist_claims` or `cookie_secure` reintroduces exactly the same holes, and `pub(crate)` fields also make in-crate struct-literal construction possible, which bypasses `build()` entirely. Add a `pub(crate)` **getter** when in-crate code needs a value. Do not add public setters, `pub` fields, or interior mutability to `OidcBffConfig`.
- **Never add `#[derive(Deserialize)]` or `Default` to `OidcBffConfig`.** With env config gone, "support a TOML/YAML file" is the obvious next request; a `Deserialize` derive constructs the struct field by field and bypasses `build()` and every check in it. `Default` is the same hole with a friendlier name. Deserialize into a separate DTO and feed the builder.
- **Builder setters must stay infallible, with all validation in `build()`.** Validating at setter time is order-dependent and silently unsound: a `post_logout_redirect_url` https-downgrade check that runs before `redirect_url` has been set has nothing to compare against and passes. `build()` is the only point where the whole config is known.
- **`cookie_name`, `cookie_secure`, and `allowed_origin` are derived from `redirect_url` in `build()` and must never get setters.** They are the cookie-hardening and CSRF-reference values; making them independently settable lets a caller pick an origin that does not match where the IdP actually redirects.
- Tokens (`access_token`, `refresh_token`, `id_token`) live only in the server-side session and are never exposed by `/auth/me` or the `Auth` extractor. The `RESERVED_SESSION_KEYS` deny-list in `session_state.rs` (not `config.rs`) keeps `persist_claims` from shadowing these keys — **this list is hand-maintained, not auto-derived**; when adding a new session key constant, add it to the constant list AND to `RESERVED_SESSION_KEYS`. The `reserved_keys_cover_every_constant` test enforces membership.
- The two deny-lists in `param_names.rs` (`DENIED_AUTH_PARAMS`, `DENIED_PASSTHROUGH_PARAMS`) are hand-maintained in the same spirit and guard the crate's two consumer-supplied parameter surfaces. Keep them sorted, deduplicated, and independent of one another; add to `DENIED_AUTH_PARAMS` whenever the crate starts emitting a new authorization-request parameter (the `deny_list_covers_every_crate_set_authorize_param` test in `handlers/login.rs` will fail if you forget). `max_age` is on that list for an unusual reason — not danger, but *unverifiability in the hand-rolled form*; removing it re-opens the silent-downgrade path that `require_auth_within` exists to close.
- `validate_return_to` (in `handlers/login.rs`, re-exported at crate root) requires a printable-ASCII absolute path (≤512 bytes) and rejects `//`, `\`, and `:/` — open-redirect protection including backslash normalization (`/\evil.com` → `//evil.com` in browsers). `return_to_prefix` is validated at startup via the same function.
- PKCE S256 is unconditional; ID-token validation only accepts the 9 asymmetric algorithms in the static `ALLOWED_ALGS` array (RS\*/PS\*/ES\*).
- Pre-auth slots (`oidc_pre_auth` vec, cap `PRE_AUTH_MAX_SLOTS = 5`) are scanned with constant-time comparison across **all** slots — no cross-slot early exit. FIFO eviction is an availability trade-off (not a security boundary); state is cryptographically validated. The cap of 5 slots (~1.1 KB serialized) is sized for `DbSessionStore`. **`CookieSessionStore` + 5 slots × a long `return_to` can exceed the ~4 KB cookie limit and silently break login** (the cookie is simply dropped by the browser). `DbSessionStore` is the supported configuration for applications that need concurrent logins (e.g. multiple open tabs).
- **Extra authorization *parameters* never enter `PreAuthEntry`; the one `max_age_secs` integer does.** An `ExtraAuthParams` set belongs to the *route*, is validated once at startup, and is applied when the authorization URL is built — the name/value pairs are never serialized into a pre-auth slot. That is a size budget, not a preference: a slot is ~220 bytes and there are 5 of them (~1.1 KB), which already sits uncomfortably inside the ~4 KB `CookieSessionStore` limit. Adding up to 8 × 512-byte values per slot would blow that budget five times over and silently break login (the browser just drops the oversized cookie). The callback does not need them either — nothing in the exchange or validation path reads them back. `PreAuthEntry::max_age_secs` is the sole, deliberate exception and the size argument is exactly what distinguishes it: one `Option<i64>` costs ~20 serialized bytes per slot that sets it and — thanks to `skip_serializing_if` — literally zero for every login that does not, and unlike the parameters the callback *cannot* do its job without it (`/auth/callback` is shared by every login route, so the requirement has no other way to travel). The rule to apply to any future request to "just put X in the slot too" is that arithmetic, not the precedent.
- **The step-(8) freshness check must stay ahead of `session.renew()` and every session write.** `verify_auth_freshness` runs immediately after ID-token validation and before anything touches the session, so a login that fails the requirement leaves **no** authenticated session behind. Moving it after `renew()`/`LOGIN_AT`/the claim inserts — or "tidying" it in next to the claim handling, where the `claims` value is also in scope — would mean a rejected step-up still hands the caller a usable session, which is the whole failure mode the feature exists to prevent. It also **fails closed on a missing `auth_time`**: OIDC Core makes the claim REQUIRED when the request carried `max_age`, so an absent claim is evidence the provider did not honour it, not a reason to skip the check. Do not "tolerate providers that omit `auth_time`". `callback_rejects_a_stale_authentication_and_establishes_no_session` asserts both the absence of every session key **and** `session.status() != Renewed` — the latter is what actually pins the ordering, since the absence assertions alone would still pass if the check moved to just after `renew()`.

- **The freshness age is measured from `entry.started_at`, not from callback arrival.** The provider evaluates `max_age` when it *receives* the authorization request, so everything the user does at the provider afterwards — consent, account selection, and above all the Application-Initiated Action the variant asked for — happens after the provider's clock has stopped. Measuring from callback arrival charges that time to the budget and rejects logins the provider honoured perfectly: the crate's own worked example (change password, 5-minute requirement) would fail any user who takes more than five minutes to fill in the form. Total flow duration is bounded separately by `pre_auth_ttl`. `auth_freshness_does_not_charge_time_spent_at_the_provider` pins this; the `AUTH_TIME_SKEW_SECS` allowance is for **clock drift between the two machines**, not for elapsed time, and should not be grown to paper over a reintroduction of this bug.

- **A step-up must complete as the same subject.** When `entry.max_age_secs` is set and the session already holds a `SUB`, the callback rejects a token whose subject differs instead of overwriting it. Providers' re-prompt screens commonly offer "use a different account", so without this a route that reads as "confirm it's you before changing your password" can be satisfied by authenticating as somebody else, silently converting the session — while the application resumes at a `return_to` it chose for the *original* subject. The check is deliberately scoped to variants that set a requirement: switching accounts via a plain login route is ordinary behaviour and must keep working (`callback_allows_a_subject_change_when_no_requirement_is_set`).

- **`require_auth_within` gates the login, not the session.** It is a precondition on completing that particular login; the session it produces is an ordinary one and carries no "stepped up" marker. Arriving at `return_to` is therefore not proof a step-up happened — the user could have navigated there with a session they already had. A handler that needs to *make a decision* on freshness must `persist_claims(["auth_time"])` and check it. Do not add a session marker without also adding it to `POST_AUTH_SCRUB_KEYS`, or a later plain login inherits the previous step-up's marker.
- **Callback passthrough is success-path only.** The IdP `error=` branch returns 400 and never redirects, so no attacker-suppliable `error_description` can ever be appended to a URL. Any change that makes the error path redirect must re-derive this from scratch; do not "unify" the two paths.
- **Extra-parameter *values* must be application constants fixed at startup — this is documentation-enforced, not type-enforced.** `ExtraAuthParams::new` takes strings and cannot tell whether a value came from a config constant or from `req.query_string()`. Deriving one from the incoming request turns every variant route into an authorization-request injection point (`acr_values`, `prompt`, `login_hint`, a provider-specific action name — all attacker-chosen). Do not add an API that accepts per-request values, and do not "helpfully" thread a request into `login_route`. If a future version needs per-request values, that is a design discussion, not a refactor.
- The callback writes the `rest` vec back to the session **before** any later failure path, so a failed exchange does not nuke concurrent tabs' pre-auth slots.
- IdP `error` callback values are logged but never reflected into responses. A stateless error redirect (no `state`) leaves the pre-auth vec intact.
- `ensure_same_origin_against` compares the precomputed ASCII origin from `cfg.allowed_origin` — never naive string prefix matching, never re-parsing the redirect URL per request.
- `revoke_best_effort` uses the crate's shared redirect-disabled HTTP client. Token values are never logged; only the endpoint URL and error kind appear in log output.
- Errors map to RFC 9457 problem+json via `BffError`'s `ResponseError` impl. Internal errors never leak detail strings to the client.
